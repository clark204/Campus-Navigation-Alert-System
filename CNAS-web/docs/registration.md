# Registration and sign-in

Finished 2026-11-01. Read this before touching registration, login, password recovery, or academic terms.

## Flow
Upload COR PDF -> confirm details -> email + password -> account is active right away, signed in, on "Verify your email" (see below).
There is no admin approval. Students with problems contact the administrator (contact info is in the site footer).

## Rules (decided, do not change without asking Clark)
- The "Scan to Verify" QR code on the COR is NOT used.
- Stored from the COR: school ID (unique), first/middle/last name, program code. Plus email, password, verified_at. The college is not stored: it comes from the program (`users.program_code` → `programs.college_id`).
- The COR PDF is never stored. Only a short-lived `registration_drafts` row is kept (expires after 30 minutes, pruned by the scheduler). The draft also carries the COR's class meetings and term id; they become the student's class schedule only when the student ticks "Also save my class schedule" on the confirm step (API: `save_schedule: true`). See `docs/schedule.md`.
- Student ID, program and college are read-only on the confirm step. The name can only be re-split, not changed.
- Duplicate student ID is rejected with a "contact the administrator" message.
- Consent checkbox is required (Data Privacy Act, RA 10173), on the web and in the app: `POST /api/register/cor` needs `consent=1` (`UploadCorWithConsentRequest`, 422 `errors.consent` without it). The app shows the same notice text as the web page.
- Only CORs for the CURRENT term are accepted. The current term is one row in `academic_terms` (is_current). Admin changes it by hand each semester in Settings → Academic term (`/admin/settings?tab=academic-term`; the old /admin/academic-terms redirects there; the app has the same screen, settings.md). The dashboard (web banner, app card) warns when there is no current term or it was set 5 months ago (`AcademicTerm::warning`, `REMINDER_MONTHS`). No current term = registration closed.
- Validator checks are all pass/fail: header text, labels, 8-digit student ID, AY + semester = current term, total units = sum of subjects, valid Date Enrolled, both printed copies match, known program code (a program missing from the `programs` table fails the COR).

## Where the code is
- `app/Services/Cor/` (CorExtractor, CorValidator, CorCheck, ParsedCor): reads and checks the COR text (smalot/pdfparser)
- `app/Services/RegistrationService.php`, `StartedRegistration.php`: shared by web and API
- Programs and colleges: `Program` (code, name, college), `College`. `User::program` is the account's program; `User::college` goes through it, so `$user->college` still works. `College::users` counts through programs.
- Schema: `users.program_code` (nullable, FK to `programs.code`, null on delete). It replaced `users.college_id` in migration `2026_11_15_090000_replace_users_college_with_program`: a user got the program of their college when that college had exactly one program; otherwise null, to be set by an admin.
- Web: `app/Http/Controllers/Auth/RegisterController.php`, routes /register, /register/cor, /register/confirm
- API (for CNAS-mobile): `app/Http/Controllers/Api/RegisterController.php`, POST /api/register/cor (`cor` + `consent`; answers with the read-only details incl. `college_name` and `meeting_count`, `CorDraftResource`) and /api/register. /api/register returns the user without a token; the app then calls /api/login.
- Login: `app/Services/LoginService.php`, web `Auth/LoginController`, API `Api/AuthController` (Sanctum tokens: /api/login, /api/me, /api/logout). Rate limit `login` (5 a minute per ID/email and IP, `AppServiceProvider`). On the page, the "try again in N seconds" wait counts down live (`session('throttle')`, `resources/js/retry-countdown.js`), and the button shows a spinner and "Signing in…" while the request runs (`data-submit-once` + `data-loading-text` in `app.js`).
- Sign-in history: `LoginActivity` model, `LoginActivityLogger`, `DeviceDetector` (kept 90 days)
- Roles: `app/Enums/UserRole.php` (admin, staff, faculty, student). After login each role lands on its own dashboard. Signed-in users cannot open the landing page.

## Email verification (built 2026-11-21)
- **Two different columns.** `users.verified_at` = COR-verified at registration. `users.email_verified_at` = the email was confirmed with a code. Never mix them. Neither is fillable. `User::needsEmailVerification()` = not admin and no `email_verified_at`.
- **Codes** (`App\Services\EmailCodes`, table `email_codes`, `EmailCode`, purposes in `App\Enums\EmailCodePurpose`: `verify_email`, `change_email`, `reset_password`): 6 digits, only a bcrypt hash stored, 10 minutes, 5 wrong tries then a new code is needed, 60 s between sends. One row per user and purpose: a new code replaces the old one. `email` is the address it went to. Every error is on the key `code`. Expired rows are pruned hourly (`routes/console.php`). Password recovery uses `reset_password` (see "Password recovery").
- **Mail**: `App\Mail\EmailCodeMail` (HTML view `mail/email-code`: tables and inline styles only, the logo `public/icons/icon-192.png` embedded as CID so it shows without the site; plain-text part `mail/email-code-text`; heading and text per purpose from `EmailCodePurpose`), queued (`ShouldQueue`). Only `.env` decides how it's sent: `MAIL_MAILER=failover` tries the Hostinger mailbox (`MAIL_*`, cnas-app@tcc-mapsafe.online) first and Gmail (`MAIL_FALLBACK_*`, mailer `smtp_fallback` in `config/mail.php`) when Hostinger refuses or is down (order in `MAIL_FAILOVER_MAILERS`). A failed mailer is skipped for 60 s per worker. Through Gmail the sender shows as the Gmail account (Gmail rewrites From). Hostinger allows 100 emails a day; past that it refuses and Gmail takes over. Without a queue worker nothing is sent (`composer run dev` runs `queue:listen`). The plain code sits in the `jobs` row until it's sent.
- **When a code is sent**: after registration, web and API (`RegistrationService::complete`, after the commit). On sign-in (web and API) of an unverified non-admin, only if they have no usable code (`sendUnlessPending`), so signing in again doesn't send another. That covers accounts the admin creates and accounts from before this feature.
- **Web**: registration signs the student in and goes to `/email/verify` (`Auth\EmailVerificationController`, `pages/verify-email-page`): code field (`autocomplete="one-time-code"`), "Resend code" with a countdown (`partials/resend-code-button`, `resources/js/resend-cooldown.js`; the server enforces the wait too), and "Wrong email address?" to fix a typo before the email is verified (otherwise a mistyped sign-up email would lock the student out, since Settings waits for verification). Success goes to the role's dashboard with an "Email verified" toast (`toast` flash, see portal.md), and Settings shows a "Verified" badge next to the email.
- **What waits for verification**: every portal route (`EnsureEmailIsVerified` on the portal group in `routes/web.php`) redirects to the verify page; guest pages redirect there too (`bootstrap/app.php`). Still open without it: /navigate, the alert banner and takeover (`/api/alerts/active`), push subscribe, "I'm safe", saved/recent places from /navigate, logout and the verify page. The API routes (e.g. /api/schedule) are not blocked; the app decides from `email_verified`.
- **The admin is exempt** (never redirected, never sent a code, `email_verified` always true) so a mail problem can't lock the admin out.
- **API** (Sanctum): `POST /api/email/verify` `{code}` → the user JSON (422 `errors.code` when wrong, expired or locked). `POST /api/email/resend` → 202 `{message, resend_in: 60}` (422 `errors.code` during the cooldown; 200 when already verified). `UserResource` has `email_verified` (bool).
- **Changing email in Settings** (admin and portals, shared `AccountController`, `partials/account-email-form`): the code goes to the NEW address and the email only changes after it's entered, so a typo can't lock anyone out. Until then the old email still signs in. While a change waits, the form asks for the code, with Resend and Cancel. Confirming also sets `email_verified_at`. Uniqueness is checked again on confirm. Errors use the `accountEmail` bag. A verified email shows a "Verified" badge and no button until a different address is typed ("Send code", `resources/js/email-change.js`). An unverified one (only the admin can reach Settings like that) shows "Not verified" and a "Verify email" button: it sends the same `change_email` code to the current address, and confirming only sets `email_verified_at`.
- **App (Sanctum, `Api\AccountController`, every role)**: the same flow and messages through `App\Services\AccountChanges`, which the web `AccountController` uses too. `GET /api/account/email` → `{email, email_verified, pending: {email, resend_in} | null}`. `PUT /api/account/email {email}` → 202 with that state and `message` (200 when it is already the verified email). `PUT /api/account/email/confirm {code}` → `{message, user}`. `POST /api/account/email/resend` → 202. `DELETE /api/account/email` cancels. Errors are 422 on `code` or `email`. Same `settings-email-code-*` limits as the Settings form. `PUT /api/account/password {current_password, password, password_confirmation}` (`Api\UpdatePasswordRequest`: the Settings rules, with the current password checked on the `sanctum` guard; `throttle:6,1`) → `{message, user}`: rotates the remember token and ends every web session and every other app token (`UserSessions::endAll(keepTokenId:)`); this phone keeps its token. Tests: `Auth/ApiAccountTest.php`.
- **Rate limits** (`AppServiceProvider`): `email-code-send` 10 an hour per user and 30 a minute per IP; `email-code-verify` 10 a minute per user and 60 a minute per IP. The Settings forms use `settings-email-code-send` / `settings-email-code-verify` (same numbers, own buckets) so the message shows on the email form. Per-IP caps are high on purpose: the campus shares one IP.

## Password recovery (built 2026-11-21)
All in `App\Services\PasswordRecovery`, shared by web and API. Every success sets the password, clears `must_change_password`, rotates the remember token and ends all web sessions and Sanctum tokens (`App\Services\UserSessions`, also used by Settings password change, the admin temporary password and account deletion).
- **Email reset** ("Forgot password?" on the login page, `/password/forgot`, `Auth\PasswordResetController`, `pages/forgot-password-page`, `pages/reset-password-page`): email or student ID (`LoginService::findByLogin`) → a `reset_password` code to the account's email, **verified or not** (Clark's decision: an unverified student must still get back in without the admin). **The reset page has two steps: the code is checked first** (`password.verify-code`, `verifyResetCode`), and only a right code shows the new-password form (Clark's request 2026-11-21). A right code is used up and becomes a one-time reset grant (random token, cache key = its hash, `GRANT_TTL_MINUTES` = 15; web keeps it in the session as `SESSION_GRANT`); `resetWithGrant` sets the password, else `GRANT_EXPIRED_MESSAGE` on `reset_token` and back to step 1. A new "Forgot password?" start forgets an old grant. The answer is always `PasswordRecovery::SENT_MESSAGE`, and every failure on the code step is `RESET_CODE_MESSAGE` (no "N tries left": a different answer for unknown accounts would show which accounts exist; EmailCodes still locks after 5 wrong tries). A resend inside the 60 s wait is skipped silently for the same reason. The typed login waits in the session (`SESSION_LOGIN`). Success sets `email_verified_at` only when the code went to the account's current email, then goes to sign in.
- **No self-service recovery without email (decided 2026-11-21).** A COR-upload recovery was built and then removed the same day: a COR isn't secret (printed, photographed, shared) and the text checks can't tell a fake one (#6 in deploy-review), so anyone with a copy could take over an existing account by choosing a new email. Don't bring it back without a real ownership check. Instead, "Can't access your email?" (`/password/no-email`, `pages/no-email-access-page`, linked from the forgot and reset pages) says: go to the CNAS administrator with your school ID; the admin fixes the email (Admin > Accounts > Edit details) and sets a temporary password (accounts.md). "Send the administrator a message" opens the site footer's concern form with the Account topic picked (`?topic=account#feedback`; the footer reads `request('topic')`), so the admin sees it in Admin > Concerns and the bell.
- **Temporary password** (admin, see accounts.md): `users.must_change_password` (not fillable). `EnsurePasswordIsChanged` (before `EnsureEmailIsVerified` on the portal group) sends the user to "Choose a new password" (`/password/change`, `Auth\TemporaryPasswordController`, `pages/change-password-page`; can't reuse the temporary one; only works while `must_change_password` is true, 403 otherwise, so a stolen session can't change the password without the current one); the same routes stay open as for an unverified email. Order after sign-in: `User::nextRoute()` = password change → verify email → home (also used by the guest redirect in `bootstrap/app.php`).
- **API**: `POST /api/password/forgot {login}` → 202 `{message, resend_in}` (same for unknown accounts). `POST /api/password/verify-code {login, code}` → 200 `{reset_token, expires_in}` (422 `errors.code`). `POST /api/password/reset {reset_token, password, password_confirmation}` → 200 (422 `errors.reset_token` when expired or used, `errors.password`). The `password-reset` limit keys step 1 by login and step 2 by the grant. `UserResource` has `must_change_password`; the API isn't blocked by it (like `email_verified`), and the app replaces it on its Change password screen (`PUT /api/account/password`, below; the temporary password is the current one).
- **Rate limits** (`AppServiceProvider`): `password-forgot` 5 an hour per login, 30 a minute per IP (key `login` on the web form); `password-reset` 10 a minute per login (step 2: per reset grant), 60 per IP. The web reset page reads the login from the session for its bucket.
